NOTE FROM THE PERSON WHO RAN THIS (read first)
----------------------------------------------
Run on 29 Oct 2026 as a Container Apps job inside the Azure network (the database has
no public endpoint, so it cannot be run from a laptop or an SSH session).

This run does NOT prove the security model survived the move, for two reasons:

1. The Azure database is EMPTY (one user, the super admin). Checks 2 and 3 print only
   zeros / "no data", so their PASS is vacuous. Check 1 passes but notes nobody has
   linked a second sign-in method yet.
2. Checks 4-7 hard-code user and organisation IDs from the old Supabase demo database
   (e.g. EMP=0639a54b-..., ORG=328bd5f2-...). Those rows do not exist here, so an UPDATE
   matches nothing and reads as "ALLOWED", and fixture inserts error out. The FAILs
   there are fixture mismatches, not evidence of a hole.

What was tested for real instead, against the live API with a throwaway employee
(since deleted): an employee could NOT set role=super_admin, is_active=false,
personal_email or login_method on their own profile (all HTTP 403, "not allowed from
this account"), while editing their own first name worked.

To get a meaningful result the gate needs the Supabase demo data copied into Azure
(same IDs), or the guard scripts changed to look users up by role.
